How I build

Framework architecture

The layering I apply to a hybrid automation framework, so that a locator change touches one file and a new banking flow reuses what already exists.

ci / trigger
Jenkins · GitHub Actions — scheduled regression runs and per-branch smoke, with tagged suites (@smoke, @regression) selecting scope
test layer
Spec files · TestNG suites — intent only: no locators, no waits, no raw driver calls
fixture / base
Playwright fixtures · WebDriver factory — browser context, auth state, test data seeding, teardown hooks
page objects
POM — one object per screen: locators plus the actions that screen supports, returning the next page object
components
Reusable banking flows — login, account selection, transaction posting, approval chains shared across specs
services
REST clients · SQL validators — API setup and assertions, plus Oracle/MySQL queries that confirm what the UI claims
data layer
Externalised test data — data providers and fixtures, with AI-generated datasets covering boundary and negative cases
reporting
Allure · Playwright HTML — traces and screenshots on failure, results analysed for failure trends, defects raised into JIRA

Regression automation for E-Banking releases

Context

E-Banking releases carry real financial risk, and the regression pack was large enough that manual execution was setting the pace of every release.

Problem

Scripts existed, but locator changes and duplicated flows made maintenance expensive — failures were as likely to be framework noise as real defects, which erodes trust in the suite.

What I did
  • Developed and implemented the test automation strategy for the banking application using Selenium WebDriver with Core Java and TestNG.
  • Built and maintained the framework on a Page Object Model base, then extended it into a hybrid structure so data, configuration and reusable flows lived outside the specs.
  • Owned script development, maintenance and troubleshooting — including the unglamorous part, keeping the suite green as the application changed.
  • Analysed execution results to identify failure trends and the areas worth automating next.
Outcome

Regression scenarios that previously ran by hand now run automatically, with reusable components cutting manual testing effort across sprint releases. The work was recognised with a “Round of Applause” award for contribution to the E-Banking automation project.

Backend data validation and AI-assisted test design

Context

In banking, a transaction that looks right on screen still has to be right in the database — and edge cases around limits, reversals and boundary values are where coverage usually thins out.

Problem

UI-only assertions can pass while persisted data is wrong, and writing exhaustive negative and boundary cases by hand competes directly with sprint execution time.

What I did
  • Executed SQL queries against Oracle and MySQL to validate backend data after UI and API operations, confirming integrity rather than appearance.
  • Managed test data used in automation scenarios so runs were repeatable and edge cases were genuinely covered.
  • Applied AI tools (ChatGPT, Claude, GitHub Copilot) to generate test cases and test data, optimise scripts and speed up defect analysis.
  • Reviewed every generated case against the requirement before it entered the suite — AI drafts the breadth, the engineer keeps the judgement.
Outcome

Improved test coverage across multiple Agile sprint releases through AI-assisted test case generation, with backend validation catching data defects that UI assertions alone would have passed.
